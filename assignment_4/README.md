# Assignment 4: Контрольные вопросы

## Вопрос 1: В чём заключается отличие гибридных вычислений от вычислений только на CPU или только на GPU?

**CPU only:**
- Универсальность, низкая latency
- Ограниченный параллелизм (4-64 ядра)

**GPU only:**
- Массивный параллелизм (тысячи потоков)
- CPU простаивает во время GPU вычислений
- Overhead передачи данных

**Гибридные (CPU + GPU):**
- Оба устройства работают одновременно
- Перекрытие операций: GPU копирует данные, пока CPU вычисляет
- Максимальное использование ресурсов

**Ключевое отличие:** Гибридные вычисления используют CPU и GPU параллельно, в то время как CPU-only или GPU-only используют только одно устройство.

## Вопрос 2: Для каких типов задач целесообразно распределять вычисления между CPU и GPU?

**Целесообразно для:**

1. **Гетерогенные данные** - разные части требуют разной обработки
   - Обработка изображений: CPU для метаданных, GPU для пикселей
   - Научные симуляции: CPU для граничных условий, GPU для регулярной сетки

2. **Большой overhead передачи данных** (20-40% времени)
   - Пока GPU копирует/обрабатывает, CPU обрабатывает другую часть

3. **Различная вычислительная интенсивность**
   - CPU для простой обработки, GPU для сложных вычислений

4. **Real-time задачи**
   - Игры: CPU для физики/AI, GPU для рендеринга
   - Автономное вождение: CPU для решений, GPU для обработки камер

5. **Pipeline обработка**
   - Несколько стадий можно распараллелить

**НЕ целесообразно:**
- Малые данные (< 1 MB)
- Простые операции (GPU ускорение < 2x)
- Частые синхронизации

## Вопрос 3: В чём разница между синхронной и асинхронной передачей данных между CPU и GPU?

**Синхронная:**
- CPU ждёт завершения передачи
- Блокирующая операция
- Простая в использовании
- CPU простаивает во время передачи

```cuda
cudaMemcpy(d_data, h_data, size, cudaMemcpyHostToDevice);
// CPU ждёт здесь
```

**Асинхронная:**
- CPU не ждёт завершения
- Требует CUDA streams и pinned memory
- CPU работает параллельно с передачей
- Сложнее в использовании

```cuda
cudaMallocHost(&h_data, size);
cudaStreamCreate(&stream);
cudaMemcpyAsync(d_data, h_data, size, cudaMemcpyHostToDevice, stream);
cpu_work();  // CPU работает пока GPU копирует
cudaStreamSynchronize(stream);
```

| Параметр | Синхронная | Асинхронная |
|----------|------------|-------------|
| Блокировка CPU | Да | Нет |
| Перекрытие операций | Нет | Да |
| Производительность | Базовая | +20-50% |
| Сложность | Низкая | Высокая |

## Вопрос 4: Почему асинхронная передача данных может повысить производительность программы?

**Основные причины:**

1. **Перекрытие вычислений и коммуникаций**
   - Пока GPU копирует, CPU работает параллельно
   - Выигрыш: 20-50% ускорение

2. **Pipeline обработка**
   - Разбить данные на чанки
   - Обрабатывать параллельно в разных streams
   - Выигрыш: до 2x для больших данных

3. **Скрытие latency**
   - Инициация передачи ~10-20 мкс
   - При async эта задержка скрывается CPU работой

4. **Full-duplex использование PCIe**
   - Одновременная передача CPU→GPU и GPU→CPU
   - Выигрыш: до 2x пропускная способность

5. **Повышение загрузки GPU**
   - GPU всегда занят либо копированием, либо вычислениями
   - Загрузка GPU: с 60% до 95%+

**Условия эффективности:**
- Pinned memory (обязательно)
- Независимые streams
- Размер данных > 1 MB

## Вопрос 5: Какие основные функции MPI используются для распределения и сбора данных между процессами?

**1. MPI_Scatter / MPI_Scatterv**
- Распределение данных от root ко всем
- Scatterv - для неравномерного распределения

**2. MPI_Gather / MPI_Gatherv**
- Сбор данных от всех к root
- Обратная операция к Scatter

**3. MPI_Reduce / MPI_Allreduce**
- Применить операцию (сумма, макс, мин)
- Allreduce - результат всем процессам

**4. MPI_Broadcast**
- Отправить одинаковые данные от root всем
- Для передачи конфигурации

**5. MPI_Allgather**
- Каждый процесс собирает данные от всех

**6. MPI_Alltoall**
- Каждый отправляет уникальные данные каждому
- Transpose операция

| Функция | От кого | Кому | Использование |
|---------|---------|------|---------------|
| Scatter | Root | Все | Распределение задачи |
| Gather | Все | Root | Сбор результатов |
| Broadcast | Root | Все | Передача конфигурации |
| Reduce | Все | Root | Вычисление статистики |
| Allreduce | Все | Все | Глобальная статистика |

## Вопрос 6: Как количество процессов MPI влияет на время выполнения программы и почему?

**Наблюдения:**
- Время уменьшается с ростом процессов
- Ускорение НЕ линейное (не 2x, 4x, 8x)
- Эффективность падает
- Overhead коммуникации растёт

**Причины:**

1. **Overhead коммуникации растёт**
   - Больше процессов → больше сообщений
   - Формула: `T_comm = α × log(P) + β × n/P`

2. **Размер локальной задачи уменьшается**
   - Каждый процесс получает меньше работы
   - Когда `T_compute < T_comm`, производительность падает

3. **Баланс нагрузки**
   - Все процессы ждут самого медленного
   - Неравномерное распределение → простой процессов

4. **Закон Амдала**
   - Последовательная часть ограничивает ускорение
   - `Speedup_max = 1 / s` где s - доля последовательного кода

5. **Архитектура системы**
   - Shared memory: эффективность 80-90% до 64 процессов
   - Ethernet кластер: 50-70% при 16 процессах
   - InfiniBand: 70-80% при сотнях процессов

**Оптимальное количество:**
```
P_optimal ≈ sqrt(N / threshold)
```

**Правило:** Используйте столько процессов, сколько нужно для целевого времени при эффективности > 60%.

## Вопрос 7: Какие факторы ограничивают масштабируемость распределённых параллельных программ?

**Основные факторы:**

1. **Закон Амдала**
   - Последовательная часть ограничивает ускорение
   - Примеры: 5% → max 20x, 10% → max 10x

2. **Overhead коммуникации**
   - Латентность: 1-100 мкс
   - Пропускная способность: 1-100 GB/s
   - Растёт с количеством процессов

3. **Баланс нагрузки**
   - Неравномерное распределение работы
   - Все ждут самого медленного процесса

4. **Синхронизация**
   - Collective операции требуют ожидания всех
   - Частая синхронизация убивает производительность

5. **Размер задачи (Granularity)**
   - `Granularity = T_compute / T_comm`
   - Должен быть > 10 для эффективности

6. **Память и cache**
   - Memory bandwidth bottleneck
   - Cache thrashing
   - NUMA effects

7. **I/O Bottleneck**
   - Все процессы пишут/читают одновременно
   - Конкуренция за дисковую систему

8. **Ограничения алгоритма**
   - Зависимости по данным
   - Глобальная синхронизация
   - Неравномерные графы

| Фактор | Влияние | Решение |
|--------|---------|---------|
| Закон Амдала | Высокое | Минимизировать последовательную часть |
| Латентность сети | Среднее | InfiniBand, батчинг |
| Load imbalance | Высокое | Динамическая балансировка |
| Granularity | Высокое | Увеличить N на процесс |

## Вопрос 8: В каких случаях использование распределённых параллельных вычислений оправдано?

**✅ Используйте MPI когда:**

1. **Данные не помещаются в память одной машины**
   - Задача требует > 256 GB RAM
   - Примеры: геномика, климатические модели, big data

2. **Вычисления слишком долгие**
   - Задача займёт дни/недели на одной машине
   - Примеры: молекулярная динамика, обучение нейросетей

3. **Задачи параллелизуются естественно**
   - Слабая связь между подзадачами
   - Редкие коммуникации (< 20%)
   - Примеры: параметрический поиск, Monte Carlo

4. **HPC-специфичные задачи**
   - Квантовая химия, CFD, физика высоких энергий

5. **Финансово оправдано**
   - ROI > 2x
   - Экономия времени критична

**❌ НЕ используйте MPI когда:**

1. **Малые задачи**
   - Размер < 100 MB
   - Время < 1 минута на одной машине

2. **Сильная связь между данными**
   - Частые коммуникации (> 50%)
   - Примеры: графовые алгоритмы, динамическое программирование

3. **Нет доступа к кластеру**
   - Используйте OpenMP, GPU, Cloud

4. **Сложность разработки**
   - Прототипирование
   - Короткий deadline
   - Нет опыта с MPI

5. **Стоимость**
   - `Cost(MPI cluster) > Cost(single node) × Speedup`

| Критерий | Используйте MPI | НЕ используйте |
|----------|----------------|----------------|
| Размер данных | > 256 GB | < 10 GB |
| Время вычислений | > 1 час | < 10 минут |
| Коммуникация | < 20% | > 50% |
| Масштаб | > 8 узлов | 1 узел достаточно |

**Пошаговый подход:**
1. Начните с single-node (OpenMP)
2. Если недостаточно, добавьте GPU
3. Только если мало, используйте MPI
4. Гибрид для максимума (MPI + OpenMP + GPU)
