# Контрольные вопросы к Assignment 3

## 1. Какие основные типы памяти существуют в архитектуре CUDA и чем они отличаются по скорости доступа?

**Ответ:**

В архитектуре CUDA существуют следующие основные типы памяти:

| Тип памяти | Область видимости | Скорость доступа | Размер |
|------------|------------------|------------------|---------|
| **Регистровая память** | Один поток | Самая быстрая (~1 цикл) | ~64 KB на SM |
| **Разделяемая память** (Shared Memory) | Блок потоков | Очень быстрая (~5-10 циклов) | 16-48 KB на блок |
| **Локальная память** | Один поток | Медленная (как глобальная) | Зависит от GPU |
| **Глобальная память** | Все потоки | Медленная (~200-400 циклов) | Несколько GB |
| **Константная память** | Все потоки (только чтение) | Быстрая при кэшировании | 64 KB |
| **Текстурная память** | Все потоки (только чтение) | Быстрая при кэшировании | Зависит от GPU |

**Соотношение скоростей:** Регистры > Shared memory > L1/L2 кэш > Глобальная память

## 2. В каких случаях использование разделяемой памяти позволяет ускорить выполнение CUDA-программы?

**Ответ:**

Использование разделяемой памяти эффективно в следующих случаях:

1. **Повторное использование данных** - когда одни и те же данные читаются несколькими потоками в блоке
   - Пример: свертка, фильтрация изображений

2. **Обмен данными между потоками** - когда потоки должны обмениваться результатами
   - Пример: reduction операции, prefix sum

3. **Изменение шаблона доступа** - когда нужно преобразовать некоалесцированный доступ в коалесцированный
   - Пример: транспонирование матриц

4. **Кэширование часто используемых данных** - загрузка данных из глобальной памяти один раз
   - Пример: умножение матриц (tile-based algorithms)

**Важно:** Разделяемая память ускоряет программу только когда польза от быстрого доступа превышает накладные расходы на синхронизацию (`__syncthreads()`).

## 3. Как шаблон доступа к глобальной памяти влияет на производительность GPU-программы?

**Ответ:**

Шаблон доступа критически важен для производительности:

**Коалесцированный доступ (эффективный):**
- Соседние потоки в варпе обращаются к последовательным адресам
- GPU объединяет запросы в одну транзакцию памяти (128 байт)
- Максимальная пропускная способность

```cuda
// Хороший пример
int idx = threadIdx.x + blockIdx.x * blockDim.x;
output[idx] = input[idx];  // Последовательный доступ
```

**Некоалесцированный доступ (неэффективный):**
- Потоки обращаются к несмежным адресам
- Требуется несколько транзакций памяти
- Пропускная способность падает в 2-10 раз

```cuda
// Плохой пример
int idx = threadIdx.x * stride;  // Доступ с большим шагом
output[idx] = input[idx];
```

**Влияние:**
- Коалесцированный доступ: ~80-90% пиковой пропускной способности
- Некоалесцированный: ~10-40% пиковой пропускной способности

## 4. Почему одинаковый алгоритм на GPU может показывать разное время выполнения при разных способах обращения к памяти?

**Ответ:**

Причины различия производительности:

1. **Количество транзакций памяти**
   - Коалесцированный доступ: 1 транзакция на варп (32 потока)
   - Некоалесцированный: до 32 транзакций на варп

2. **Эффективность использования шины памяти**
   - При некоалесцированном доступе часть загруженных данных не используется
   - Впустую тратится пропускная способность

3. **Кэширование**
   - L1/L2 кэш эффективен при последовательном доступе
   - При случайном доступе процент попаданий в кэш низкий

4. **Латентность памяти**
   - Глобальная память: ~200-400 тактов
   - При неэффективном доступе латентность не может быть скрыта вычислениями

**Пример:** Одна и та же операция сложения массивов может работать в 5-10 раз медленнее при некоалесцированном доступе.

## 5. Как размер блока потоков влияет на производительность CUDA-ядра?

**Ответ:**

Размер блока влияет на несколько аспектов:

**1. Occupancy (загруженность SM):**
- Слишком большие блоки (>512) → мало блоков на SM → низкая occupancy
- Слишком маленькие блоки (<64) → недостаточно потоков для скрытия латентности

**2. Использование ресурсов:**
- Регистры и разделяемая память делятся между блоками
- Большой блок может исчерпать ресурсы SM

**3. Гранулярность:**
- Размер должен быть кратен размеру варпа (32)
- Неоптимальные размеры (например, 100) тратят ресурсы впустую

**Оптимальные значения:**
- 128-512 потоков на блок (чаще всего 256)
- Должно быть кратно 32 (размер варпа)
- Обеспечивать как минимум 2-4 блока на SM

**Экспериментальные данные (из Task 2):**
- 32 потока: низкая производительность (недостаточно потоков)
- 256-512 потоков: оптимально
- 1024 потока: может быть избыточно (ограничивает число блоков на SM)

## 6. Что такое варп и почему важно учитывать его при разработке CUDA-программ?

**Ответ:**

**Определение:**
Варп (warp) - это группа из 32 потоков, которые выполняются синхронно на одном мультипроцессоре (SM). Все потоки в варпе выполняют одну и ту же инструкцию одновременно (SIMT модель).

**Почему важен:**

1. **Единица планирования**
   - GPU планирует выполнение на уровне варпов, а не отдельных потоков
   - Блок потоков делится на варпы (например, блок 256 = 8 варпов)

2. **Дивергенция ветвлений**
   ```cuda
   if (threadIdx.x < 16) {
       // Часть варпа выполняет это
   } else {
       // Другая часть выполняет это
   }
   // Обе ветки выполняются последовательно → замедление
   ```

3. **Коалесцированный доступ**
   - Память загружается транзакциями для целого варпа
   - 32 потока варпа должны обращаться к последовательным адресам

4. **Оптимальные размеры**
   - Размер блока должен быть кратен 32
   - Размер 100 → 3 полных варпа + 4 неиспользуемых потока в 4-м варпе

**Рекомендации:**
- Избегайте дивергенции в варпах
- Используйте размеры блоков кратные 32
- Оптимизируйте доступ к памяти на уровне варпов

## 7. Какие факторы необходимо учитывать при выборе конфигурации сетки и блоков потоков?

**Ответ:**

**Основные факторы:**

1. **Характеристики устройства:**
   - Число мультипроцессоров (SM)
   - Максимум потоков на блок (обычно 1024)
   - Максимум блоков на SM (зависит от архитектуры)
   - Объем разделяемой памяти

2. **Ресурсы на блок:**
   - Регистры: ограничивают число активных блоков
   - Shared memory: при большом использовании уменьшает occupancy
   - Локальная память: может снизить производительность

3. **Размер задачи:**
   - Число элементов для обработки
   - Grid size = (N + block_size - 1) / block_size

4. **Occupancy (загруженность):**
   - Число активных варпов на SM
   - Цель: достичь occupancy ~50-75% для скрытия латентности
   - Используйте CUDA Occupancy Calculator

5. **Шаблон доступа к памяти:**
   - Размер блока влияет на коалесценцию
   - Учитывайте размер кэш-линии (128 байт)

**Практические рекомендации:**

```
Размер блока: 128-512 (чаще 256)
Число блоков: минимум = число_SM * 2-4
Размер варпа: всегда 32 (кратность обязательна)
```

**Пример расчета:**
```
GPU с 20 SM, задача на 1M элементов:
- Block size: 256
- Grid size: (1000000 + 255) / 256 = 3907 блоков
- Блоков на SM: 3907 / 20 ≈ 195 (отлично для occupancy)
```

## 8. Почему оптимизация CUDA-программы часто начинается с анализа работы с памятью, а не с изменения алгоритма?

**Ответ:**

**Причины приоритета оптимизации памяти:**

1. **Memory-bound приложения**
   - Большинство CUDA-программ ограничены пропускной способностью памяти
   - Вычислительная мощность GPU огромна (TFLOPS), но память медленная
   - Пример: простое сложение массивов - GPU ждет данные из памяти

2. **Разница в скорости:**
   ```
   Вычисления:  ~10 TFLOPS
   Память:      ~500-900 GB/s

   Соотношение: 1 байт данных = ~10 FLOPs
   ```
   Если алгоритм не выполняет много операций на байт, он memory-bound.

3. **Эффект от оптимизации:**
   - Коалесцированный доступ: ускорение в 5-10 раз
   - Использование shared memory: ускорение в 2-5 раз
   - Алгоритмические улучшения: зависит от задачи

4. **Относительная простота:**
   - Оптимизация доступа к памяти не меняет логику алгоритма
   - Можно применять паттерны (tiling, coalescing)
   - Изменение алгоритма может потребовать полной переработки

5. **Профилирование показывает:**
   ```
   nvprof ./program

   Часто видим:
   - 80% времени: ожидание памяти
   - 20% времени: вычисления
   ```

**Порядок оптимизации:**
1. Обеспечить коалесцированный доступ
2. Использовать shared memory для повторного использования
3. Оптимизировать occupancy (размеры блоков)
4. Только потом менять алгоритм

**Вывод:** Даже идеальный алгоритм работает медленно при плохом доступе к памяти. GPU может выполнять триллионы операций в секунду, но только если данные доставляются достаточно быстро.
